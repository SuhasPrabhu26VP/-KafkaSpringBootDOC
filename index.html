Part 01 — Foundations

Core Kafka Concepts

The 18 building blocks behind every Kafka producer and consumer app — topics, partitions, brokers, delivery guarantees, and the Spring Kafka configuration that wires them together. Examples throughout use a PayPal → SAP Commerce payment flow to keep things concrete.

Producer

C-01 ⌥ KafkaProducerConfig ⌥ KafkaMessageProducer
An application that publishes events to Kafka topics, sending records to specific topics with optional keys for partitioning.

Example — PayPal acts as producer: after collecting user credentials, it initiates the transaction and sends critical transaction details to SAP Commerce for later confirmation or reconciliation.

Consumer

C-02 ⌥ KafkaConsumerConfig ⌥ KafkaMessageConsumer
An application that reads events from Kafka topics, processing records at its own pace with control over offset commits.

Example — the SAP Commerce Order Service consumes payment events: it reads the PayPal transaction details and updates order status without rushing or blocking the customer.

// Consumer Configuration Properties

PropertyWhat It Does

AUTO_OFFSET_RESET_CONFIGDecides where to start reading when no committed offset exists for this consumer group — see values below
KEY_DESERIALIZER_CLASS_CONFIGConverts message key bytes back into the original type (e.g. String) so the consumer can read it
VALUE_DESERIALIZER_CLASS_CONFIGConverts message value bytes back into your domain object (e.g. via KafkaAvroDeserializer). In practice this is usually set to ErrorHandlingDeserializer, which wraps your real deserializer to handle bad messages gracefully — see below

Topic

C-03 ⌥ KafkaTopicConfig
A logical category that organizes related events, similar to a database table or a folder in a filesystem.

Example — the payment-transactions topic stores every payment event from PayPal or other payment providers.

Partition

C-04 ⌥ KafkaTopicConfig
A physically ordered, immutable sequence of events within a topic that enables parallel processing and horizontal scaling. A topic with 3 partitions can be processed by up to 3 consumers in parallel within a single consumer group.

Example — by default, Kafka assigns a record to a partition by hashing its key (hash(key) % numPartitions), so every payment for the same userId lands on the same partition and is processed in order. Records with no key are spread round-robin across partitions instead. Routing specific payment types to specific partitions on purpose is a custom strategy — see Custom Partitioner.

Offset

C-05 ⌥ KafkaMessageConsumer
A unique, sequential ID for each event within a partition that lets consumers track their reading position and resume from failures.

Example — offset 45 means SAP Commerce has successfully processed 45 PayPal transactions on that partition and will resume from transaction 46 after a restart or crash.

Consumer Group

C-06 ⌥ KafkaConsumerConfig
A set of consumers that work together to read from a topic, where each partition is assigned to exactly one consumer in the group at a time.

Example — three SAP Commerce payment processors form a consumer group reading a 3-partition topic; each instance is assigned a different partition, so every transaction is processed exactly once across the group, and no two instances fight over the same partition.

// Partition Assignment Strategies

Determines how the group leader hands out partitions to group members during a rebalance.

StrategyWhat It Does
RangeAssignorAssigns consecutive partitions per topic to each consumer (Consumer1 gets 0,1; Consumer2 gets 2,3)
RoundRobinAssignorAlternates partitions like dealing cards (Consumer1 gets 0,2; Consumer2 gets 1,3)
CooperativeStickyAssignorMinimizes partition movement during rebalance for near zero-downtime rolling restarts

Kafka clients negotiate an assignor from PARTITION_ASSIGNMENT_STRATEGY_CONFIG; check your client version's default list rather than assuming RangeAssignor alone, as recent versions ship a fallback chain that includes CooperativeStickyAssignor.

Broker

C-07 ⌥ KafkaProducerConfig
A single Kafka server that stores data, handles client requests, and manages partitions and replicas.

Example — Broker 1 stores all payment events from the last 7 days and serves them to SAP Commerce whenever needed for reconciliation.

Cluster

C-08 ⌥ KafkaProducerConfig
A group of Kafka brokers working together for scalability, fault tolerance, and high availability.

Example — three brokers run together; if one goes down during a Black Friday traffic spike, the other two keep serving payment events to SAP Commerce without interruption.

Leader & Follower

C-09 ⌥ KafkaTopicConfig
For each partition, one broker acts as leader, handling all reads and writes, while follower brokers replicate its data for fault tolerance.

Example — Broker 1 leads partition 0 for PayPal payments; Brokers 2 and 3 replicate everything it writes. If Broker 1 goes down, one of the in-sync followers is promoted to leader automatically.

ISR (In-Sync Replicas)

C-10 ⌥ KafkaTopicConfig
The set of replicas — the leader plus every follower fully caught up with it — that are eligible to satisfy acks=all, guaranteeing data durability and consistency.

Example — a partition has 3 replicas: 1 leader + 2 followers. Both followers are fully caught up, so ISR = 3. If one follower falls behind, ISR drops to 2 (the leader and the remaining caught-up follower) — writes are still safe with acks=all, but durability margin has shrunk until the lagging follower catches back up.

Record Batch

C-11 ⌥ KafkaProducerConfig
A group of events sent together from producer to broker to improve network efficiency and storage throughput.

Example — PayPal sends 1,000 transaction records in one network call instead of making 1,000 separate calls to Kafka, dramatically cutting per-message network overhead.

Retention Policy

C-12 ⌥ KafkaTopicConfig
Rules that determine how long events are kept, based on a time duration, a storage size limit, or both.

Example — keep all payment events for 90 days for audit compliance; after that, Kafka automatically deletes the oldest transactions to free up disk space.

Consumer Rebalance

C-13 ⌥ KafkaRebalanceListener
The process of reassigning partitions among consumers when a consumer joins, leaves, or fails within a consumer group.

Example — one SAP Commerce payment processor crashes; Kafka automatically reassigns its partitions to the other two processors with no manual intervention. With CooperativeStickyAssignor this happens incrementally rather than stopping every consumer in the group at once.

Dead Letter Queue (DLQ)

C-14 ⌥ KafkaConsumerConfig
A special topic that stores messages which failed processing after all retry attempts have been exhausted.

Example — a transaction with an expired credit card fails 3 retry attempts; it moves to the DLQ, where a SAP Commerce admin can review it and contact the customer manually.

// DeadLetterPublishingRecoverer

After all retries fail, this takes the failed message and publishes it to a dead letter topic instead of just dropping it.

Schema Registry

C-15 ⌥ KafkaProducerConfig
A service that stores and validates Avro/Protobuf/JSON schemas to ensure compatibility between producers and consumers as schemas evolve.

Example — PayPal adds a currencyCode field to the transaction schema; the existing SAP Commerce consumer keeps working unchanged, because the registry's BACKWARD compatibility check rejects schema changes that would break it.

Custom Partitioner

C-16 ⌥ DepartmentPartitioner
A user-defined strategy, set via PARTITIONER_CLASS_CONFIG, that overrides Kafka's default key-hash partitioning and routes a message to a partition based on business logic or message content.

Example — custom logic routes PayPal transactions to partition 0, Stripe to partition 1, and any transaction above $10,000 to partition 2 for separate, slower fraud-review processing.

Idempotent Producer

C-17 ⌥ KafkaProducerConfig
A producer configuration (ENABLE_IDEMPOTENCE_CONFIG=true) that assigns each message a sequence number per partition so the broker can detect and discard duplicates created by producer retries — exactly-once delivery within a single partition. Coordinating exactly-once writes across multiple partitions or topics needs the Transactional Producer below.

Example — a network blip causes PayPal's client to retry a send it thinks failed; the idempotent producer recognizes the duplicate sequence number and the broker keeps only one copy, so the customer is charged once, not twice.

Transactional Producer

C-18 ⌥ KafkaMessageProducer ⌥ KafkaProducerConfig
A producer that can atomically send multiple messages across partitions and topics, where all messages succeed together or fail together — built on top of the idempotent producer plus a transaction coordinator.

Example — a successful payment sends both a payment-confirmed event and an inventory-reserved event in one transaction; if inventory reservation fails, the payment event is rolled back too, so no order is left half-processed.

Stream-Stream Joins

K02 ⌥ StreamStreamJoinTopology
Co-partitioning required. Both streams must have the same number of partitions and use the same partitioning strategy. All stream-stream joins require a JoinWindows — records must arrive within the window to be matched.

// Asymmetric Inner Join

Stream B can only join with Stream A records that arrived before it — .before(Duration.ZERO).after(...). Stream A cannot join with future Stream B records.

// Windowed Inner Join with Grace Period

Adds a grace period after the window closes to accept late-arriving records. Records that arrive during grace are still matched before the window is finalized.

// Symmetric window — records within ±5 min of each other
JoinWindows symmetricWindow = JoinWindows
        .ofTimeDifferenceWithNoGrace(Duration.ofMinutes(5));

// With grace period — accepts late records up to 30s after window closes
JoinWindows windowWithGrace = JoinWindows
        .ofTimeDifferenceAndGrace(Duration.ofMinutes(5), Duration.ofSeconds(30));

// Asymmetric — B must follow A (B only looks back, not forward)
JoinWindows asymmetricWindow = JoinWindows
        .ofTimeDifferenceWithNoGrace(Duration.ofMinutes(10))
        .before(Duration.ZERO)
        .after(Duration.ofMinutes(10));

streamA.join(streamB, (userA, userB) -> userA.getUserId() + " | " + userB.getStatus(),
        symmetricWindow,
        StreamJoined.<String, AvroUser, AvroUser>as("store-ss-inner")
                .withKeySerde(Serdes.String())
                .withValueSerde(userSerde)
                .withOtherValueSerde(userSerde))
        .to("join-stream-stream-inner-v1");

Stream-Table Joins

K03 ⌥ StreamTableJoinTopology
Co-partitioning required. The stream and table must share the same key. If the stream is keyed differently (e.g. userId joining a companyId-keyed table), use selectKey() first — this triggers an automatic internal repartition topic.

// Inner Join

Emits a result only when the stream record has a matching key in the KTable. If the table has no entry for that key yet, the stream record is dropped.

// Left Join

Always emits a result for every stream record. If no match in the table, the table side is null. Useful for enrichment where reference data may not exist yet.

// Versioned (Temporal) Join

Uses a versioned state store to look up the table value at the time the stream event occurred — not the latest value. Requires Stores.persistentVersionedKeyValueStore().

// Rekey stream to match KTable key before joining
KStream<String, AvroUser> usersRekeyed = userStream
        .selectKey((userId, user) -> user.getCompanyId(),
                Named.as("rekey-user-to-companyId"));

KTable<String, AvroCompany> companyTable = builder
        .table("company-topic",
                Consumed.with(Serdes.String(), companySerde),
                Materialized.as("store-company-lookup"));

usersRekeyed
        .join(companyTable,
                (user, company) -> user.getFirstName() + " works at " + company.getName())
        .to("join-stream-table-inner-v1");
Important: Each topic can only be registered once per StreamsBuilder. Do not register the same topic as both a regular KTable and a versioned KTable — this will throw a TopologyException.

Table-Table Joins

K04 ⌥ TableTableJoinTopology
Standard Table-Table join requires the same key on both sides. If your tables have different keys (e.g. userId vs companyId), use a Foreign Key join — it extracts the FK from the left table internally and handles the key mismatch without rekeying.

// Foreign Key Join — KTable to KTable

Left table is keyed by userId, right table by companyId. A KeyValueMapper extracts companyId from the user record to look up the company — no manual rekey needed.

// Standard join — both tables must share the same key
userTable.join(companyTable,
        (user, company) -> user.getName() + " at " + company.getName(),
        Materialized.<String, String, KeyValueStore<Bytes, byte[]>>as("store-tt-inner"))
        .toStream()
        .to("join-table-table-inner-v1");

// Foreign Key join — user keyed by userId, company keyed by companyId
userTable.join(companyTable,
        user -> user.getCompanyId(),     // FK extractor
        (user, company) -> user.getName() + " at " + company.getName(),
        Materialized.<String, String, KeyValueStore<Bytes, byte[]>>as("store-tt-fk"))
        .toStream()
        .to("join-table-table-fk-v1");
Topic conflict: Do not use the same topic (e.g. user-topic) as both a KStream source in one topology and a KTable source in another — they share one StreamsBuilder and Kafka Streams will throw InvalidTopologyException. Use dedicated changelog topics for Table-Table joins.

GlobalKTable Joins

K05 ⌥ GlobalTableJoinTopology
No co-partitioning required. A GlobalKTable is fully replicated to every application instance. The KeyValueMapper at join time extracts the lookup key from the stream record — the stream does not need to be rekeyed first.

// Inner Join

Emits a result only when the KeyValueMapper finds a matching key in the GlobalKTable. Stream records that resolve to a key not in the table are dropped.

// Left Join

Always emits a result for every stream record. If the KeyValueMapper resolves to a key not in the table, the table side is null — useful while the global table is still loading at startup.

GlobalKTable<String, AvroCompany> globalCompany = builder
        .globalTable("global-company-topic",
                Consumed.with(Serdes.String(), companySerde),
                Materialized.as("store-global-company"));

// KeyValueMapper: (streamKey, streamValue) -> lookupKey in GlobalKTable
userStream
        .join(globalCompany,
                (userId, user) -> user.getCompanyId(),   // no selectKey() needed
                (user, company) -> user.getName() + " at " + company.getName())
        .to("join-global-inner-v1");
Conflict: A GlobalKTable and a KTable cannot both be registered from the same source topic in the same topology. Use a dedicated topic for the GlobalKTable (e.g. global-company-topic).

// Decision Guide

Is the data event-shaped (something happened)? └── YES → KStream Is the data entity-shaped (current state of something)? ├── Is the dataset large (millions of rows)? │ └── YES → KTable (partitioned, scalable) │ └── Is the dataset small (thousands of rows)? └── YES → GlobalKTable (no co-partitioning, simpler joins)

// Code Patterns

// KStream — Event Processing
KStream<String, AvroUser> userStream = builder
        .stream("user-topic", Consumed.with(Serdes.String(), userSerde));

// KTable — Latest State Lookup
KTable<String, AvroCompany> companyTable = builder
        .table("company-topic",
                Consumed.with(Serdes.String(), companySerde),
                Materialized.as("store-company-lookup"));

// GlobalKTable — Replicated Lookup (No Co-partitioning)
GlobalKTable<String, AvroCompany> globalCompany = builder
        .globalTable("global-company-topic",
                Consumed.with(Serdes.String(), companySerde),
                Materialized.as("store-global-company"));

// Stream-Table Join (requires selectKey for co-partitioning)
userStream
        .selectKey((k, user) -> user.getCompanyId())
        .join(companyTable,
              (user, company) -> user.getName() + " works at " + company.getName());

// Stream-GlobalTable Join (no co-partitioning needed)
userStream
        .join(globalCompany,
              (userId, user) -> user.getCompanyId(),
              (user, company) -> user.getName() + " works at " + company.getName());

Key Rules to Remember

K07 ⌥ KafkaStreamsConfig
  • 🚫
    The same topic cannot be registered as both KTable and GlobalKTable in the same topology — throws TopologyException at startup.
  • 🚫
    The same topic cannot be registered as both KStream and KTable in the same topology — use dedicated changelog topics for Table-Table joins.
  • ⚙️
    Enable topology optimization to automatically merge duplicate KStream source registrations: 
    spring.kafka.streams.properties.topology.optimization=all
  • 🏷️
    Name every processor with .withName() and Named.as(). Duplicate processor names across topologies sharing the same StreamsBuilder cause TopologyException.
  • 🌍
    GlobalKTable loads all data at startup before processing begins. Keep it small or face slow restarts. Ideal for reference data under a few hundred MB.
  • 🔑
    Co-partitioning = same number of partitions + same partitioning strategy + same key type. Violated co-partitioning causes silent data loss — no errors, just missing join output.
  • 🔗
    KTable FK join handles key mismatch internally — no manual selectKey() needed: 
    userTable.join(companyTable, user -> user.getCompanyId(), ...)
  • ⏱️
    Stream-Table inner join timing: if a stream record arrives before the KTable is populated, it is dropped — no retry. Start the company generator before the user generator to pre-populate the KTable.
  • 🔄
    Exactly-once processing (processing.guarantee=exactly_once_v2) requires Kafka brokers ≥ 2.5 and at least 3 replicas. All KafkaTemplate.send() calls must run inside executeInTransaction() or a @Transactional method.
  • 🗝️
    Key format must match exactly between producer and consumer. Mismatched formats (e.g. COMP-05 vs COMP-005) cause inner joins to produce zero output with no error — always log and verify key values.
